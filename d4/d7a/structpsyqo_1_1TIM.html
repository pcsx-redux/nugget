Detailed Description

A reader for Sony's TIM texture container.

TIM is the devkit's texture format, and is what most PS1 games ship. It is a thin wrapper: a short file header, then one optional CLUT section and one pixel section, each carrying a destination in VRAM and its dimensions, followed by data that is already in the layout the GPU wants. There is no compression and no decoding, so loading one is a validation pass and two transfers.

The dimensions in a TIM section are in 16-bit VRAM units rather than in texels, which happens to be exactly what GPU::uploadToVRAM wants, so the section headers drop almost directly into a Rect.

Validation is mostly a build-time concern. A TIM you produced yourself either loads or visibly does not, and paying for those checks in every shipped binary buys nothing, so define DEBUG_TIM to get them. The one exception is always compiled in: a section whose declared size disagrees with its dimensions is rejected unconditionally, because that is the only failure that is not visible. It catches a bad width, the width is what the transfer length comes from, and the result is a write past the end of the buffer rather than a wrong picture.

enum class psyqo::TIM::Error : uint8_t

Why a TIM was rejected.

Explicit rather than a bool because the failures mean genuinely different things: a compressed TIM is a valid file this parser refuses, while a truncated one is a broken asset.

The enum keeps its shape in every configuration on purpose. All but BadSectionSize require DEBUG_TIM to be produced, but a type whose definition changes between builds is how a header and a library end up disagreeing, so the values stay put and simply go unused.

The pixel format of the data, as declared by the file.

This is only a hint about how to view the pixels. The data is copied into VRAM the same way regardless, so treat this as the source for a texture page's colour mode rather than as something to branch on. Mixed means the file holds several formats at once.

void psyqo::TIM::upload ( GPU &  gpu) const

Uploads the texture, and its palette if it has one, to the VRAM coordinates the file itself asks for.

Convenient for assets authored alongside the code that loads them, and the wrong choice as soon as anything decides placement at runtime, since the file wins. Prefer the overload taking explicit positions when the application owns the VRAM layout.

This is a blocking transfer with the same rules as GPU::uploadToVRAM: no other GPU transfer may be in flight. Called while a frame is running, use GPU::waitChainIdle first.
